  7. 「为什么每个 AI Agent 都还长成 while (true) 的样子?」——把可追加事件日志当唯一真相源 — dev.to 周榜上最工程化的一篇。诊断:几乎所有 Agent 运行时都是同一个骨架——内存里放一坨可变状态,调模型规划、执行工具、更新状态、循环。四个结构性毛病:①中断只能靠 hack——进程被杀在半路,那个状态对象里躺着一次「做了一半的迭代」,它并不诚实地反映真实发生过什么;②重试全是特例,每种失败模式加一段 try/catch,越滚越复杂;③并行工具调用很别扭,要么串行、要么自己管 promise 再拼结果,又多出一堆状态;④没法回退——状态是一堆可变对象,你无法从对话中途分叉,也无法重放「模型当时到底看到了什么」。替代方案:让只追加的事件日志成为唯一真相源,状态退化成日志的一个投影。每条消息、每次工具调用、每个结果、每次文件编辑都是 EventStore 表里的一行(sequence / event_id / type / payload_json / caused_by / thread_id);运行时读日志尾部、派发给 handler、把结果追加回去——「一轮」是一次状态转移,不是一次循环迭代。几个很有意思的设计副产品:没有「新建对话」按钮(会话永久存在,Agent 自己投影日志尾部来管理上下文);只给模型一个 cli 工具(read/write 有结构化 handler,其余透传给 shell,每次调用就是一个事件);caused_by 指针让对话天然是树形的,分叉是原生能力;TUI / 桌面端 / JSON-RPC / 一次性 CLI 共用同一条事件流;不同工作区的 Agent 之间用 tell 事件通信,互不泄漏对方的项目上下文;还有一个可选技能读自己的事件日志当证据去复现 bug、写测试、提 PR。作者对代价也很诚实:等于把一个真数据库放进热路径,要考虑重放成本、日志体积和快照;上千事件的长会话需要定期物化快照(还没实现);而且任何不进日志的东西都变成看不见的副作用。项目叫 Pizza,开源在 tomsun28/pizza。
    为什么值得关注:这是对昨天 apache/maka「append-only 事件日志」那条的完整理论说明。最值得抄的不是整套架构,而是那个判断:Agent 的可观测性、可中断、可分叉、可复现,其实是同一个问题——你有没有一份诚实的历史记录。 如果你正在给自己的 Agent 加「断点续跑」或「回到第 N 轮重来」,这篇能省你一次重构。
