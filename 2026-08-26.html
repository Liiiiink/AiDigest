  1. GitHub:上线前到底该怎么评测 LLM——误报砍掉 95%,靠的是把 recall 设成不可谈判的门禁 — 用 LLM 给 secret scanning 降误报的完整方法论。几条可以直接抄的做法:指标分三层——主结果(误报率/精确率)、安全约束(recall,降幅超出预设范围就一票否决)、运营护栏(延迟/成本/可靠性);把离线评测当集成测试跑,prompt、模型、输入构造、流水线逻辑每动一次就重跑一遍,并记录 prompt 版本 + 模型 + 数据集版本 + 系统配置;一次只改一个变量,prompt 改动和模型升级分开评;评测数据必须保留生产的脏(周围的真实代码、附近的干扰值、残缺上下文、奇怪格式)——干净数据集会掩盖真实失败;生产标签当噪声信号而非 ground truth(开发者关掉告警的原因五花八门:轮换了、接受风险了、只是想解阻塞);失败案例人工归因到「模型/prompt/输入/流水线/数据集/标签」六类。最终结果:离线数据集上误报降 95%,recall 守在护栏内。
    为什么值得关注:今天最有含金量的一篇工程复盘。「recall 当硬门禁 + 一次一个变量 + 保留生产的脏」这三条,基本就是把 LLM 从 demo 推上线的全部难点。

  3. 潜伏六年的 Go 运行时 bug:32 位系统上 netpoll 会把 socket 认成 eventfd — 32 位 ARM / i386 上长时间运行的 Go 程序会崩在 runtime: netpoll: eventfd ready for something unexpected。根因很精妙:Go 在 epoll_event 那 8 字节的 ev.Data 里塞了两种不同的东西——eventfd 用的是裸指针,socket 用的是「高 4 字节存地址、低 4 字节存 fdseq 标签」的 tagged pointer。32 位小端机器上裸指针只占低 4 字节,而比较代码把 ev.Data 转成 uintptr(32 位下就 4 字节)只看低半部分——于是裸指针地址和 fdseq 标签撞在了同一片位上。等 fdseq 涨到约 300 万(正好是 netpollEventFd 落在地址空间头 3MiB 的地址范围),netpoll 就开始把 socket 当成 eventfd。排查用了 pmap 查地址、LLM 辅助扫 32 位下的整数转换坑、最后写出几分钟必现的复现器。修法:eventfd 也改存「打了标签的 nil pollDesc」,让 ev.Data 永远是 tagged pointer。这个 bug 从 Go 1.14(2020)就在,活了六年。
    为什么值得关注:嵌入式和跨位宽移植的经典雷区——「指针里偷低位存标签」这个技巧在 64 位上天经地义,换到 32 位就直接失效。
    实战Lobste.rs2026-08-25
  4. 把 Rust enum 换成一个 64 位字,解释器全线快了 17% — Plush 解释器原本用 Rust tagged enum 表示动态值:payload 64 位 + tag 8 位,但对齐之后每个值实打实占 16 字节。作者改成经典的低位打标签方案:整数左移 2 位(低位 00,62 位范围,加减和比较可以直接在带标签的字上做,不用拆包);浮点用 2024 年 Melançon/Serrano/Feeley 论文的自标签旋转技巧(加偏置再旋转,让低两位变成 10,只损失两位指数、尾数精度全保);nil/true/false 等立即数用 5 位子标签;堆对象 8 字节对齐所以低 3 位天然是 0,正好拿来当标签位。结果每个 benchmark 都变快,平均约 17%,而作者原本预期打包/拆包的开销会拖慢它。两个原因:一是值从 16 字节缩到 8 字节,指针密集的 binary_tree/linked_list 内存流量直接减半;二是旧 enum 让 LLVM 生成的机器码非常烂——值被拆到多个寄存器和内存位置,频繁溢出到栈。Int64 + Int64 的快路径从 52 条指令 / 24 次访存 / 4 个分支 降到 36 / 9 / 1,因为现在一个值就是一个寄存器。LLVM 甚至自己发现了「把两个 tag 或起来一次分支测完」的优化。
    为什么值得关注:一个反直觉但可复用的性能教训——数据表示决定编译器能生成什么代码,而不只是决定占多少内存。
    实战Lobste.rs2026-08-25
  5. 24 核构建机加了 CPU 亲和性,构建反而更慢了——因为热 — 常识说把任务钉在固定核上能靠缓存局部性提速,这里被完整推翻了。现代机器上snoop 邻居的 L1 缓存非常快,所以进程在核间迁移的代价极低;而每个构建 job 都在热循环里烤特定的那几个核,钉住 = 单核迅速升温 = 热节流提前触发。不设亲和性时,操作系统那套半随机的任务乱窜反而把热量摊匀到整片芯片上,让节流来得更晚;构建里并行度低的阶段,迁移还顺便让每个核轮流空闲了一会儿,散热更好。
    为什么值得关注:缓存未命中的代价已经小到打不过热节流了。凡是在长时间满载的机器上调度密集任务(构建、批量推理),先量热,再谈亲和性。
    实战Lobste.rs2026-08-25
  6. 家里四张卡跑本地大模型的完整踩坑记:先修 PCIe P2P,再谈并行策略 — 四张 AMD Radeon Pro V620(各 32GB),PCIe 3.0、大多只跑到 x8,没有 NVLink / Infinity Fabric。最大的发现是卡间 DMA 压根没工作,所有 GPU→GPU 传输都在绕 CPU 内存(~7GB/s)。两个根因:BIOS 的 MMIO High Base 设太高(56T),而有些 GPU 只有 44 位寻址、需要地址落在 16T 以下——改成 4T / 1024G 粒度;内核参数加 iommu=pt——修之前卡间带宽只有 0.46GB/s 且推理输出乱码后内核 panic,修完稳定在 5~7GB/s。修复前后的对比很吓人:Gemma4-31B 双卡张量并行从 ~20 tok/s 跳到 47 tok/s,四卡从坏掉的 0.5 tok/s 恢复到 37 tok/s。其余结论:推测解码是最大的一笔收益(草稿模型让生成速度大约翻倍,但草稿模型必须完整放在单张卡上,而且它和主模型共享的层落在不同 GPU 时 llama.cpp 会出问题,需要 PR #26636);batch size 调到 4096 明显有用,microbatch、n-gram、flash attention 开关、线程数、NUMA 都没用;「共享张量放显存 + 路由专家放内存」这套跑大 MoE 的常见建议被作者直接否掉了——四通道 DDR4 下只要溢出到系统内存就掉到 8 tok/s 以下。
    为什么值得关注:本地部署最贵的时间往往浪费在「以为是模型/框架问题,其实是 BIOS 和 IOMMU」。这篇把排查顺序摆明白了:先验 P2P 带宽,再选并行策略,最后才调参。

今日新词

  • TBT(Time Between Tokens,token 间隔):模型吐出相邻两个字之间的间隔时间。它决定了你「看着它打字」时的流畅感——今天 OpenAI 用「同等 TBT 下的吞吐」来比较芯片,意思是:在保证同样打字流畅度的前提下,我能同时伺候多少人。这比单纯比峰值吞吐更贴近真实服务。
  • tagged pointer(打标签的指针):一个省内存的老技巧。因为内存里的对象通常按 8 字节对齐,指针的最低 3 位永远是 0——白白浪费了,不如拿来存「这个值到底是什么类型」。今天两条新闻都栽在或受益于它:Go 的 netpoll bug 是 32 位下标签位和地址撞车,Plush 解释器则靠它把每个值从 16 字节压到 8 字节、白赚 17% 速度。
  • speculative decoding(推测解码):让一个又小又快的「草稿模型」先一口气猜出后面好几个 token,再让大模型一次性批量验证——猜对了就白赚,猜错了才回退。它是本地部署里性价比最高的提速手段,今天那篇四卡实测里直接把生成速度翻了一倍。
  • recall / precision(召回率 / 精确率):评测里最常被搞混的一对。召回率 = 该抓的漏了多少(密钥扫描漏报一个真密钥就是事故),精确率 = 抓来的里面有多少是冤枉的(误报太多没人愿意看告警)。GitHub 那篇的核心方法就是:只允许优化精确率,召回率一旦跌破护栏就一票否决——因为这两件事的代价根本不对等。
  • YAGNI(You Aren't Gonna Need It):极限编程的老口号,「你不会需要它的」。意思是别为想象中的未来需求提前写代码。今天火起来的 ponytail 把它放在了「懒惰阶梯」的第一级——让 Agent 动手前先问一句:这段代码有必要存在吗?
