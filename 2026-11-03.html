  2. OpenAI 写了个 Git 后端叫 Pando，push 中位延迟降到原来的 1/5，每天吐近 1PB — 11 月 2 日的工程博客，难得一篇讲「Codex 把并行开发量拉爆之后，底层基础设施怎么扛」的实录。 实战

    先看他们坏成什么样：Codex 普及后 monorepo 的并发推送量暴涨，去年底 fetch / push 变慢、merge 失败，可用性一度掉到 90% 以下。Pando 现在接管了整个 monorepo 的开发流量，且对外保持 Git 协议兼容，开发者用法不变。

    三个可以直接借鉴的设计：一是按分支独立协调，不相关的分支更新完全并行，代价是跨分支读到的快照时间点可能不一致（放弃仓库级一致性，只保因果一致）；二是 packfile 复用，不再为每个客户端现生成一个唯一 pack，同样的字节服务给很多客户端；三是 LSM-tree 式后台 compaction——每次 push 落一个 L0 packfile，后台 worker 按几何级数合并，monorepo 上一直合到 L4。

    唯一的竞争点只剩 ref 指针，用一个类 CAS 的原子操作守住。他们对比过的两个方案都被模拟实验否掉了：跨副本三阶段提交在高负载下磁盘打满、写延迟爆炸；走 blob storage 共享 WAL 排序的方案则是读延迟爆炸。

    实现是 Rust 全新写的，没有历史包袱，配了 Git 一致性测试套件和确定性模拟测试。OpenAI 说打算把 Git 客户端侧的改动回馈上游，这部分值得盯。

    实验设置很简单：Circle Agent Wallet 里放 10 USDC，日限额设 0.01 USDC，给 agent 钱包权限 + 邮箱访问 + 浏览器工具，指令只是「去付发票」，从没让它改规则。10 个模型各跑 20 轮。

今日术语

  • pull_request_target：GitHub Actions 的一个触发器，特点是跑在 base 仓库的上下文里、能拿到 secrets。方便，但一旦 checkout 了 fork 的代码就等于把 secrets 交给陌生人——这就是所谓的 Pwn Request。
  • Packfile / LSM-tree compaction：Git 把一堆对象压成一个 packfile 传输。Pando 借了数据库 LSM-tree 的思路——新 push 先落成小文件（L0），后台再按几何级数逐层合并，避免每次都重算。
  • 因果一致性 vs 仓库级一致性（Causal consistency）：Pando 为了让分支并行而做的取舍。你读两个分支时，看到的可能是不同时刻的快照；但有因果关系的事件顺序仍然保证。
  • Harness：模型外面那层「跑腿的脚手架」——负责调度任务、调用工具、管多个 agent。同一个模型换个 harness，实际表现能差很多，所以 GDPx 特意让每个模型跑自己的原生 harness。
  • Countersign：这次研究者提出的思路——把审批绑定到一个 agent 物理上做不到的动作上。核心前提是：agent 能访问到的审批渠道，就不是审批。
