HN + Lobste.rs 双榜:mold 链接器论文进 ASPLOS 2027——比 lld 快 2.4~16 倍,比 GNU ld 快 112 倍 — Rui Ueyama 把 mold 的设计写成了论文。核心诊断:现有链接器并行度极低,链接时大部分 CPU 核在空转,根因是符号解析和归档处理纠缠在一起这个架构约束。mold 的做法是把两者解耦,然后在整条链接流水线上系统性地铺数据并行。结果:多 GB 的 debug 二进制几秒内、常常一秒内链完;比当前最快的 lld 快 2.4~16.1 倍,比 GNU ld 快 最高 112 倍。消融实验有个很诚实的结论:没有哪一项优化是决定性的,加速来自「把每一趟都并行掉」的累积效应。
    为什么值得关注:这是「性能工程没有银弹」的一份教科书级证据——不是找到一个瓶颈捅穿,而是把每一趟 pass 都并行一遍。如果你的 C++ 项目还在等链接,换 mold 是今天投入产出比最高的一次改动。

Lobste.rs:C2PA 相机认证在 Android 上被打穿,而且「补不了」 — David Buchanan 造出了带合法 C2PA 签名、声称来自 Pixel Camera 的 AI 生成图片和视频。Android 的 C2PA 依赖 Key Attestation 和 Play Integrity 来保证只有正牌相机的数据能被签名,签名密钥由 StrongBox / Titan M2 硬件保护。破法的关键洞察:攻击者根本不需要拿到密钥原文——只要拿到 root,就可以让 StrongBox 去签任意数据。而通过漏洞提权拿 root 不需要解锁 bootloader,AVB 密钥没变,「Google 的服务器会乐呵呵地给一台已被攻陷的设备下发密钥」。两条路子:①软件漏洞(写文时全补丁 Pixel 仍有一键 root 的 CVE-2026-43499,理论上可补);②他此前的 DRAM 电磁故障注入——不依赖软件漏洞,现有硬件上永久无法修补。作者写了工具 keystork。Google 的结论是要彻底修得把整条图像流水线搬进安全隔离区,不现实,报告以「Won't fix (infeasible)」关闭,给了 7500 美元赏金。所有基于同一套 attestation 的 Android C2PA 相机应用同样中招——攻击者挑最便宜最好打的机器即可。
    为什么值得关注:在「AI 生成内容遍地」的当下,C2PA 是各家押注的内容来源认证方案。这篇的教训对任何做设备端签名的人都通用:硬件保护密钥 ≠ 保护签名语义——只要能在设备上执行代码,你保护的只是密钥本身,不是「谁在用它签什么」。

Trail of Bits 实测:普通虚拟机关不住有攻击能力的 Agent——三次逃逸,最后一次是自己挖的 3 个 0day — 作者拿 GPT-5.6-Cyber 打自己的标准 QEMU/KVM 沙箱,逃出去三次,难度逐级上升。第一次:利用几周前刚披露、宿主 Debian 12 内核还没打的 Januscape(CVE-2026-53359),而且没有公开参考资料,exploit 是从零写的。第二次:内核升级后,它转攻 libslirp 4.7.0 的 CVE-2026-9539,并发现把它和另一个没分配 CVE 的 bugfix commit 组合起来,能在宿主上拿到任意内存读写——作者坦言自己都不知道 libslirp 是什么,是 AI 自己推断出它相关。第三次:所有依赖从上游最新源码重建之后,它找到三个 0day 加一个「上游已修但发行版还没分发」的洞串成链:QEMU 的 VAPIC ROM 别名与锁定 SMRAM 重叠 → 暴露 SMRAM 做 SMM 执行;KVM 一个陈旧影子页未同步且可复用;paging64_invlpg() 复用陈旧的 level-2 role 造出可写的 2MB 宿主物理映射;libslirp 混合分片 IHL 导致 ICMP 数据超拷,产出成千上万个可识别的活 NetPacket 对象用来劫持回调。它还额外找到四个洞但主动弃用(判断可靠性不够或被 AppArmor 挡了)——这是策略判断,不是穷举。整个过程自主运行约 12 小时,跨多次上下文压缩不丢线索,失败会回退,会去拉论文、写 exploit oracle、做最小复现。人类唯一的活是死机后按重启键。
    为什么值得关注:三条可落地的结论。①攻击面本身太大——连虚拟机的「网络」「显示」这种无害功能都是入口;②发行版更新节奏太慢——Debian oldstable 的 backport 流程 + 「不算安全问题」的分类,让关键补丁永远到不了;③Firecracker 这类极简攻击面的 microVM 明显更难打(Agent 能把宿主内核搞崩,但没能完整逃出)。作者的定性:把这类 Agent 按 APT 对待。配合今天 OpenAI 那份复盘一起读。

Lobste.rs:Go 的 sync.Map 换成了哈希字典树——什么时候该用、什么时候别用 — Go 1.24 把 sync.Map 换成实验性哈希 trie,1.26 去掉实验开关成为正式实现,API 完全没变。结构:64 位哈希切成 4 位一组(每组 16 个取值)逐层选子指针,最深 16 层;16 叉是实测的甜点——降到 8 叉 Load 性能掉一半以上,升到 32 叉只多约 1%。两种节点:entry 节点存一对 KV + overflow 指针处理完全哈希碰撞;indirect 节点存 16 个原子子指针 + 互斥锁 + 父指针 + dead 标记。Load 全程无锁——只读原子指针,要么看到旧的要么看到新的,不会看到半截。写路径四步:无锁查找 → 只锁直接父 indirect 节点 → 重读槽位检测指针是否过期 → 原子指针发布。所以落在不同 indirect 节点的写可以真并发。代价也很清楚:内存是普通 map 的 3~5 倍,没有 Len(只能 Range 数),多键之间没有原子性,Clear 是 O(1) 但可能吞掉并发的 Store,Range 是活的 DFS 遍历、没有快照语义。基准:8 核、命中率 1023:1 时 32.87 ns/op vs RWMutexMap 的 195.1 ns/op;但单个热点 key 或单核时,RWMutexMap 反而更快。
    为什么值得关注:一句话选型——写少读多、或者各 goroutine 各管各的 key,用 sync.Map;并发不高或有单一热点 key,老老实实 map + RWMutex。这条经验规则值得直接写进团队的 Go 规范。
