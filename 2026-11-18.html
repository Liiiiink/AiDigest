    成因很具体:OpenJDK 用一段手写汇编拿 AVX-512 加速 Base64 解码,一个很短的畸形输入会在 Java 把它判为非法之前,先往缓冲区尾部外写 62 字节(Oligo 描述为整数下溢)。Calif 的 Quang Luong 发现,并演示了在 Jira、Confluence、Jenkins、Keycloak 上的免认证 RCE。

    先判断自己中不中,三个条件要同时成立:① JDK ≥ 17.0.6(2023 年 1 月起,含 21 / 25 / 27,任何厂商的构建——Corretto、Temurin、Microsoft OpenJDK、Zulu、Red Hat OpenJDK 都算);② CPU 是带 AVX-512 VBMI 的 x86-64(Intel Xeon Ice Lake~Granite Rapids、AMD EPYC Zen 4+),JVM 需报 avx512_vbmi + avx512bw 且 UseAVX >= 3;③ 跑的是 HotSpot。17.0.6 以前的版本、标准 OpenJDK 8 和 11、ARM64、OpenJ9、Azul Prime/Zing 都不受影响;java.util.Base64 的 MIME 解码器走标量路径,也不受影响。

    动作:升到 17.0.21.0.3 / 21.0.13.0.3 / 25.0.5.0.3 / 27.0.1.0.3。暂时不能升就加 JVM 参数 -XX:-UseBASE64Intrinsics(影响面最小,只是 Base64 变慢;更窄的写法是 -XX:+UnlockDiagnosticVMOptions -XX:DisableIntrinsic=_base64_decodeBlock)。-XX:UseAVX=2 也能挡,但会关掉全部 AVX-512、拖慢其他计算,而且在 ARM 上会直接起不来。可以用 JAVA_TOOL_OPTIONS 下发,打完补丁记得把参数撤掉。优先排查对外暴露的那批:Keycloak、Jira、Confluence、Artifactory、Jenkins、PingFederate。

今日术语

  • Intrinsic(内建函数):JVM 把某些热点标准库方法(比如 Base64 解码)替换成手写汇编来提速的机制。好处是快,坏处是绕过了 Java 的内存安全——今天 Java4Shell 的越界写,正是写在这类手写汇编里。
  • AVX-512 VBMI:Intel/AMD 服务器 CPU 上的一组宽向量指令,能一次处理 64 字节。因为只有部分 CPU 有,所以今天这个漏洞同一份 JAR,换台机器可能就打不中。
  • Pre-auth RCE(免认证远程代码执行):攻击者不需要任何账号密码,只要能往服务发请求,就能让它执行自己的代码。是漏洞里最高一档的危害。
  • Flaky Test(不稳定测试):同样的代码、同样的环境,有时过有时不过的测试。它最大的危害不是烦人,而是教会 agent「失败了再跑一次就行」——所以 Claude Code 团队明确禁止 agent 用重试、加 sleep 的办法糊弄过去。
