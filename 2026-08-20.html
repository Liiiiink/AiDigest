OpenAI 给前沿模型上「零数据留存」:Private Safety Processing 想同时要安全和隐私 — 8 月 19 日发布。此前存在一个死结:最严重的 AI 安全风险往往只在「多次交互」中才看得出来(比如反复试探护栏、Agent 任务逐步偏离原意),但现有的 ZDR 兼容安全系统只能孤立评估单次调用——结果就是某些前沿模型部署强制要求客户开放内容留存,与金融、医疗等行业的合规义务直接冲突。OpenAI 的解法是 Private Safety Processing:内容可存在客户自己的基础设施上，或存在 OpenAI 侧但用客户持有的密钥加密(OpenAI 不掌握密钥);检测到风险时,OpenAI 只收到一个「活动类型」的窄信号,客户用自己的系统去查、要不要申诉再自行决定分享。目前小范围预览，9 月放出技术白皮书并扩大推送。

    为什么值得关注:全文最该抄进设计文档的三条原则:①先在环境层做容器化,再在模型层做行为引导——模型层在 Claude Code auto 模式下能拦住约 83% 的过度行为,剩下的靠硬边界兜底;②隔离强度要匹配用户的监督能力——开发者能看懂 bash,知识工作者不能,所以后者必须上 VM;③警惕自研组件——「每一次部署里,标准原语都扛住了,出问题的都是我们自己在周边写的东西」。那个 allowlist 事故尤其扎心:白名单必须当成「能力授予」来设计,而不只是目的地过滤。

Bun 1.4 的 Rust 重写不太妙:一个月 15.8k 次机器人提交,5000+ 个未合 PR — Lobste.rs 热帖,今年最值得读的一份「AI 大规模改代码」的反面观察。①发版停滞:距上一个稳定版已超三个月,是 Bun 自 2022 年以来最长的间隔,而此前会给具体日期和数字的官方账号,现在只剩反复的模糊承诺——Jarred Sumner 那条「博客明天发」的推文已经成了社区笑话。②代码来源失衡:一个月内 15.8k 次提交来自 robobun、1.6k 来自 autofix-ci[bot],Jarred 本人只有 790 次;Sumner 自己承认「Bun 的大部分 PR 都是 Claude 在 prompt Claude」。仓库有 5000+ 个 open PR——远超 GitHub 建议的 1000 上限(对比 React 是 441)。③质量质疑:Zig 作者 Andrew Kelley 公开表示,他和其他人「看到 Bun 代码库里的编程实践,越来越感到惊恐」,形容为「hack 上面叠 hack」和「滥用断言」。④重写理由站不住:官方说重写是因为 Zig 的内存安全问题,但新的 Rust 代码里有大量 unsafe 块,理由自相矛盾。作者怀疑真实动机是「向世界展示 Claude 有多强」,让整件事「更像一支 Anthropic 广告」——而「用 AI 去改进有纪律的 Zig 代码」这个选项从未被认真考虑过。
    为什么值得关注:这是目前规模最大、最公开的「AI Agent 托管生产级代码库」实验,而它正在给出不乐观的中期读数。三条可直接迁移的教训:①PR 积压量是 AI 协作失控的先行指标——5000 个未合 PR 意味着「生成」已经彻底跑赢「审查」;②「AI 写的」不等于「AI 维护得了的」;③重写理由要经得起代码检验——如果你为了内存安全换语言,结果满屏 unsafe,那你换的是语法不是安全。作者也点出了赌注:这件事的成败,Anthropic 的声誉也在牌桌上。

LLM 时代的可扩展软件:让用户「说一句话」就给自己造功能 — HN 106 分。核心论点:大多数 Web 软件只服务需求曲线的头部,长尾的小众需求永远得不到满足——因为为小众加功能会把所有人的 UI 搞复杂。LLM 让「生成定制代码」的成本趋近于零,于是可以换一种架构:一个测试完备的内核 + 稳定的扩展点,用户描述需求,LLM 生成一小段代码挂到扩展点上,安全地写、部署和分享。作者称之为「LLM-native software」。最有价值的是他列出的扩展原语必须具备的五个性质:①执行经济——闲置近零成本、单次调用几分钱的零头;②冷启动快——请求路径上的代码要在个位数毫秒;③可强制的限额——CPU、内存、网络、日志、响应体积全部要有界;④强隔离——租户间的故障与安全隔离,包括 Spectre 防护;⑤基于能力(capability)的安全动作——不要把裸 API key 或 fetch 暴露给不可信代码,而是传入窄能力引用(比如一个「只能取这一封已批准邮件」的函数),这样无需复杂代理逻辑就能防住凭据泄露与数据外泄。技术选型上他梳理了解释器(Lua/QuickJS)、V8 Isolates(Cloudflare Workers、isolated-vm)、microVM(Firecracker/libkrun/Deno sandbox)、WASM/WASI,并认为 Cloudflare Dynamic Workers 是 2026 年最接近生产可用的方案。
    为什么值得关注:这篇和上面那篇 Anthropic 容器化的文章说的是同一件事的两面——当代码由不可信来源(LLM 或用户)生成,「沙箱 + 能力模型」就从可选项变成地基。第 ⑤ 条尤其值得抄:给不可信代码传窄能力函数,而不是凭据,这一个设计决策能消掉一整类外泄风险。作者也诚实提醒:做平台真的很难,别低估设计、运维和调试的投入。

  • 零数据留存(Zero Data Retention, ZDR):企业调 API 时的一种承诺——你发过去的提示词和模型回答,处理完就删,不留档、OpenAI 员工也看不到、不拿去训练。金融、医疗这类行业必须要这个才敢用。今天的新闻里,难点在于「不留存」和「要靠多轮记录才能发现坏人」互相打架,OpenAI 用「内容加密在客户手里、只回传一个风险类型的信号」来两头兼顾。
