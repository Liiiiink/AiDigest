模型精讲:MoE(混合专家)——万亿参数的模型,为什么跑起来像个小模型

DeepSeek V3 有 6710 亿参数,但每吐一个字只用掉 370 亿——省下的那 94%,是 MoE 干的

核心看点:与其让一个"全才"回答所有问题,不如养一屋子"专才",每次只叫醒两个。参数量可以无限堆,计算量却几乎不涨。

它是什么

标准 Transformer 的每一层里都有一个前馈网络(FFN),负责"思考加工"。它是模型里参数最多的部分,而且每个 token 经过时,整个 FFN 都要算一遍。

MoE(Mixture of Experts,混合专家) 做的事很直接:把这一个大 FFN,拆成很多个小 FFN——每一个叫一个专家(expert)。再配一个路由器(router,也叫门控网络 gating network),由它决定"这个 token 该交给谁处理"。

关键在于:路由器只挑少数几个专家激活,其余的这一步完全不参与计算。这就是所谓的稀疏(sparse)。

于是模型出现了两个截然不同的参数量:

  • 总参数(total):所有专家加起来,决定模型能"装下多少知识"
  • 激活参数(active):每个 token 实际用到的,决定"算得有多慢"

为什么重要

一句话:它把"模型多大"和"跑得多慢"这两件事解耦了。

在 MoE 之前,想让模型更聪明,唯一的办法是把它整个变大——变大 10 倍,推理就慢 10 倍。MoE 打破了这个绑定。看几组真实数字:

| 模型 | 总参数 | 激活参数 | 激活占比 | |---|---|---|---| | DeepSeek V3 | 671B | 37B | 5.5% | | Qwen3-235B-A22B | 235B | 22B | 9.4% | | Llama 4 Maverick | ~400B | 17B | 4.3% | | MiniMax-M2 | ~230B | 10B | 4.4% |

注意 Qwen3 的命名 "A22B"——那个 A 就是 Active,厂商已经把激活参数直接写进模型名里了。看懂这个命名,你就看懂了半个 2026 年开源模型圈。

顺手学一个常识:Mixtral 8x7B 这个名字很容易误导人。它不是 8×7B=56B,而是约 47B——因为只有 FFN 层被拆成了 8 份专家,注意力层等其余部分是所有专家共用的,不该重复计数。

它是怎么工作的:一家有 256 个科室的医院

把标准大模型想象成一个全科医生:不管你来看什么病,都是他接诊,他脑子里装着所有科室的知识。看一次病,他把整个知识库过一遍。

MoE 则是一家分科医院:

  1. 分诊台(路由器):你一进门,分诊台看一眼你的症状,给每个科室打个分(其实就是一次线性变换 + softmax)
  2. 挑出 Top-K:只挑分最高的 K 个科室(常见是 top-2,Switch Transformer 激进到 top-1),其余科室今天根本不上班
  3. 加权汇总:被选中的科室各自给出诊断,按分诊台给的权重加权合并,得到最终结果

训练时这些"科室"分工是自己长出来的,没人预先指定。 研究者事后去看,发现编码器里确实会冒出"标点符号专家""专有名词专家"这种。但也别浪漫化——在多语言场景下,并没有出现"中文专家""英文专家",分工比人的直觉抽象得多。

进阶点 1:路由器会"偏心",得靠辅助损失掰回来。 训练早期某几个专家碰巧被多选中,就会被训得更好,于是更容易被选中——正反馈死循环,最后变成几个专家累死、其余闲置。解法是在训练目标里加一项 辅助损失(auxiliary loss / load balancing loss),专门惩罚"分配不均",逼路由器把 token 摊平。你在 TRL 里看到的 router_aux_loss_coef、训练日志里的 aux_loss,就是这个东西。ST-MoE 还加了 router z-loss,惩罚过大的路由 logits,让 softmax 数值更稳。 🔬 进阶点 2:还有一种"永远上班"的共享专家。 DeepSeek V3 设了 shared expert(共享专家)——不管路由器怎么选,它对每个 token 都激活。思路是:标点、语法这类人人都要用的通用模式,不该让 256 个专家每个都单独学一遍;交给共享专家兜底,其他专家就能腾出容量去学更专门的东西。不过这不是定论——Qwen3 就明确去掉了共享专家,开发者给的理由是"没看到足够显著的收益",还有推理优化上的顾虑。

天下没有免费的午餐

MoE 最该记住的一条代价:省的是算力,不是显存。

  • 算力真的省了:Mixtral 8x7B 用 top-2 路由,每步只做 2 份 7B 的矩阵乘,推理速度接近一个 12B 的稠密模型
  • 显存一点没省:所有专家的权重都得完整装进显存——Mixtral 需要能放下约 47B 模型的显存。你付的是大模型的内存钱,拿的是小模型的速度

另外两个实践中的坑:

  • 微调更容易过拟合。稀疏模型在小数据集上泛化明显更差,需要更强的正则化(比如给稀疏层单独设更高的 dropout)。有趣的是,2023 年 "MoEs Meets Instruction Tuning" 发现 MoE 从指令微调中的获益远大于稠密模型——Flan-MoE 相对 MoE 的提升,明显超过 Flan-T5 相对 T5
  • 能力分布不均。在同等预训练困惑度下,稀疏模型在知识密集型任务(如 TriviaQA)上表现格外好,但在推理密集型任务(如 SuperGLUE)上反而不如稠密模型
别把"专家越多越好"当真。研究显示专家数增加确实提升样本效率,但超过 256~512 个之后收益急剧递减,而显存却是实打实地一路涨上去。

动手教程:用 LoRA 微调一个属于你自己的小模型

只训练全模型 0.04% 的参数,产出一个 几 MB 的"人格补丁"——这就是 LoRA

你将做出:一个微调过的 Qwen3-0.6B。训练产物不是几个 G 的模型文件,而是一个几 MB 的 adapter,可以随时挂到原模型上、也可以随时摘下来。

准备:

  • Python 3.9+(PEFT 的最低要求)
  • 一张 GPU。0.6B + LoRA 门槛很低,免费的 Google Colab T4 就够跑;本地有 8GB 显存的卡也行。纯 CPU 能跑通流程但会非常慢
  • 一个 Hugging Face 账号(下载模型用,免费)
  • 装依赖:
  pip install trl peft transformers datasets

跟着做:

  1. 先搞懂 LoRA 到底改了什么(30 秒,但别跳)。 新建 peek.py,看一眼"可训练参数"这个数字:
   from transformers import AutoModelForCausalLM
   from peft import LoraConfig, get_peft_model, TaskType

   model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen3-0.6B")

   peft_config = LoraConfig(
       task_type=TaskType.CAUSAL_LM,
       r=8,                          # 秩:低秩矩阵有多"薄",8/16/32 是常用值
       lora_alpha=32,                # 缩放因子,实际缩放量 = lora_alpha / r
       lora_dropout=0.1,
       target_modules=["q_proj", "v_proj"],   # 只改注意力里的 Q 和 V 投影
   )

   peft_model = get_peft_model(model, peft_config)
   peft_model.print_trainable_parameters()

输出里那个 trainable% 就是全部重点。官方文档在 Llama-3.2-1B 上的同类示例是:524,288 / 1,236,338,688 = 0.0424%——12 亿参数的模型,你只动了 52 万个。

原理一句话:原权重 W 整个冻住不动,旁边挂两个又瘦又小的矩阵 A 和 B,只训练它们。前向变成 h = Wx + BAx。因为 B×A 是低秩分解,参数量断崖式下降。

  1. 真正跑一次微调。 新建 train.py。TRL 的 SFTTrainer 直接吃 peft_config,不用自己写训练循环:
   from datasets import load_dataset
   from trl import SFTTrainer, SFTConfig
   from peft import LoraConfig, TaskType

   dataset = load_dataset("trl-lib/Capybara", split="train[:2000]")   # 先切 2000 条跑通

   trainer = SFTTrainer(
       model="Qwen/Qwen3-0.6B",
       train_dataset=dataset,
       peft_config=LoraConfig(
           task_type=TaskType.CAUSAL_LM,
           r=8, lora_alpha=32, lora_dropout=0.1,
           target_modules=["q_proj", "v_proj"],
       ),
       args=SFTConfig(
           output_dir="qwen3-0.6b-my-lora",
           learning_rate=1e-4,              # 注意!见下方提醒
           num_train_epochs=1,
           per_device_train_batch_size=2,
           gradient_accumulation_steps=8,   # 显存不够就调大这个,别调大 batch_size
       ),
   )
   trainer.train()
   trainer.save_model()

跑起来后盯住日志里的 loss 和 mean_token_accuracy:loss 缓慢下降 = 正常;完全不动 = 学习率太小;突然变 NaN = 学习率太大。

最高频的一个坑:学习率。SFTConfig 的默认 learning_rate 是 2e-5,那是给全量微调用的。训 LoRA 时你只在学少量全新初始化的参数,TRL 官方文档明确建议用约 1e-4(高一个数量级)。照抄默认值的结果通常是"跑完了,但模型好像什么都没学会"。
  1. 看看产出物有多小。 训练完去 qwen3-0.6b-my-lora/ 目录下看:
   ls -lh qwen3-0.6b-my-lora/

你会发现只有两个核心文件:adapter_config.json(记录你用了什么配置)和 adapter_model.safetensors(那两个小矩阵)。官方文档里那个 opt-350m 的 LoRA 例子,adapter 只有 6.3 MB——而完整模型约 700 MB。

  1. 挂上去用一下。 新建 infer.py:
   from peft import AutoPeftModelForCausalLM
   from transformers import AutoTokenizer

   model = AutoPeftModelForCausalLM.from_pretrained("qwen3-0.6b-my-lora")
   tok = AutoTokenizer.from_pretrained("Qwen/Qwen3-0.6B")

   msgs = [{"role": "user", "content": "用一句话解释什么是低秩分解"}]
   ids = tok.apply_chat_template(msgs, add_generation_prompt=True, return_tensors="pt")
   out = model.generate(ids.to(model.device), max_new_tokens=128)
   print(tok.decode(out[0], skip_special_tokens=True))

AutoPeftModelForCausalLM 会自动读 adapter_config.json,把基座模型拉下来再把 adapter 贴上去——你不用手动管这个拼装过程。

  1. (可选)把 adapter 焊死进模型。 推理时基座 + adapter 分开,会有一点点额外延迟。要上线的话可以合并:
   merged = model.merge_and_unload()
   merged.save_pretrained("qwen3-0.6b-merged")

合并后 W_new = W + (alpha/r) × B×A,变回一个普通模型,推理零额外开销。代价是失去了"随时换 adapter"的灵活性。

做完你会:真正理解为什么现在满 Hugging Face 都是几 MB 的 LoRA 文件——一个基座 + N 个 adapter,就能服务 N 个不同场景,而不用存 N 份完整模型。 下一步可以探索三个方向: - 扩大 target_modules:从 ["q_proj", "v_proj"] 扩到包含 k_proj、o_proj 乃至 MLP 层的 gate_proj/up_proj/down_proj。可训练参数变多、效果通常更好,显存也涨——这是最值得你亲手做一次的 A/B 对比 - QLoRA:把基座模型量化成 4bit 再挂 LoRA,给 SFTTrainer 传一个 quantization_config=BitsAndBytesConfig(...) 即可。这是在消费级显卡上微调 7B~13B 模型的标准做法 - 多 adapter 热切换:peft_model.add_adapter(...) + peft_model.set_adapter(...),一个基座模型上挂多套 LoRA,按请求切换。这正是很多 LoRA 服务平台的底层玩法 顺带一提:本期精讲的 MoE 和这里的 LoRA,骨子里是同一种智慧——别让所有参数都参与每一次计算。MoE 在推理时做稀疏,LoRA 在训练时做稀疏。
