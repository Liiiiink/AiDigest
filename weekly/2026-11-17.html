本周热点

10 月那批凭据这周开始结账,而且轮换救不了

Cursor 认了:10 月那个带 SSH 后门的 Claude Code 扩展,源头是 Fireworks AI 被偷走的密钥

  • 发生了什么:链条现在完整了——攻击者拿到从 Fireworks AI 泄出的凭据 → 用它从 Cursor 和 Fireworks 共享数据的只读存储桶里拷数据 → 把改过的扩展塞进 Cursor 扩展市场的缓存层。构建和发布系统全程没被攻破,被攻破的是分发路径。Cursor 的处置是下架扩展、市场整体下线、配合云厂商打掉攻击者服务器、轮换凭据、重建扩展市场、重新部署生产基础设施,并把推理流量整体迁出 Fireworks。
  • 凭什么算热点:持续性是本期最硬的一条——同一条线本周被 11-11 和 11-15 两份日报接力提到,而且 11-11 那条本身是 Fireworks 两周内第二次失守(10-24 从一家第三方云厂商横向打进来,泄的三类里包含部分客户的模型权重和数据集)。多源:BleepingComputer、The Register 同步报道,11-09 到 11-11 至少 6 家安全/科技媒体跟进 Fireworks 那边。强制性:已经中招的机器,Cursor 明确说光卸载扩展不够。日报自己标的是「本周第 3 次」。
  • 你该不该动手:立刻试,而且要按新的顺序做。上期我把这条列成「没下文」,现在它有了下文,动作也跟着变了:不只是清你机器上的后门,而是去 Fireworks 签发方那边轮换你在上面存过的全部 key——在 Fireworks 上「删掉」一个存储的 secret 不等于吊销它背后那条凭据,得回到签发方(云厂商、第三方 API)重新轮换。再去翻 usage / inference 日志找不认识的调用,确认自己传过哪些数据集和模型上去;10-24 前后跑过 evaluation job 的,那些 job 用到的 key 一律当已泄露处理。动机被归为 LLMJacking——偷来的访问权转卖,所以「看不出数据损失」不是不轮换的理由。

wfx-loot:4837 个被盗 GitHub 账号试探了 61,764 个仓库,至少 1806 个真的跑起了 CI 密钥窃取器

  • 发生了什么:11-10 开始、11-12 被 Aikido 公开。偷的范围覆盖仓库/环境/组织三层 secret、GITHUB_TOKEN、OIDC 和 Actions 运行时令牌、AI 服务 key、runner 进程内存里的密钥,外加 .env / *.tfvars / *.tfstate。要害不是偷密钥,是它留的后门能活过轮换:改写 AWS role 信任策略成 "Principal": {"AWS": "*"}、在 Entra ID 里新建名为 wfx-ci-* 的联合身份凭据、伪造通过的 status check。它还会主动申请 OIDC 令牌去换 AWS / Azure / GCP 的实时会话——哪怕这个仓库压根没配过云。
  • 凭什么算热点:多源够硬——Aikido / SafeDep / Phoenix Security 三家独立复盘,11-12 起多家安全媒体跟进。采用度口径这里是反过来的:Aikido 数到 1806 个仓库真跑起了窃取器,SafeDep 独立数到 8093 个带恶意 commit 的仓库——两个数字差这么多,是因为它得手一分钟内就回滚改动并删掉运行记录和日志,所以 1806 大概率偏低。强制性和持续性也都成立:失陷账号和 10 月那波 GhostAction 高度重叠,10 月的受害者这次被复用的概率高约 1000 倍,100 多个仓库是直接在 10 月留下的 workflow 文件上又加了一层。
  • 你该不该动手:立刻试,但查的顺序和你的直觉是反的——先查云端,再查密钥。排查清单照着做:去 CloudTrail 里找名为 wfx-<pid> 的会话、审一遍 role 信任策略、删掉不认识的 wfx-ci-* 联合身份凭据、查 Vault / K8s 里用 Actions 令牌做的登录。仓库侧的特征是 PR 标题 docs: dependency audit notes、分支名 wfx-docs 或 chore/[a-z0-9]{8},但最可靠的痕迹是 Actions 历史里缺号的 run。Aikido 的判定口径很硬:只要那个试探 PR 开到过你仓库,这个账号就算已失陷,哪怕窃取器没跑起来。硬化动作四条:GITHUB_TOKEN 默认只读、workflow 文件加 CODEOWNERS、环境加审批人、收窄 OIDC 信任条件。另外 Go 模块 github.com/onuragtas/docker-env 的 v1.0.278 / v1.0.280 带毒。

「从 N 个选项里挑一个」这类活,正在被整体搬下聊天模型

Amazon 把工单打标从 Sonnet 4.6 换成决策模型:每百万工单 $22,200 降到 $500,延迟砍 78%

  • 发生了什么:两位 Amazon 工程师 11-09 发的实战文。活儿很窄——内部工单系统,每张工单从 20 个标签里选一个。实测结果:平均单次调用 4215ms → 897ms,每张工单 token 6724 → 2010。架构是工单事件进 SQS → Lambda → SageMaker 端点,用 AppConfig 做三路开关让两个模型同时吃线上流量对账。
  • 凭什么算热点:真人用过 + 产线数据,这是本期证据最实的一条——不是 benchmark,是跑在 Amazon 内部工单流上的对照。采用度:HN 717 分(11-10 记录)。结构性成立且是量级级别的:单次调用 token 降到 30%、延迟降到 21%,这不是调参能调出来的差距,是换了一类模型。另外它和同周 Google 发 Decisions API 构成多源——两家在一周内指向同一件事。
  • 你该不该动手:排进这个月,但要带走的是方法不是数字。省钱数字先打折:速度和 token 是实测,美元是推算——按每百万工单约 $21,700 的差额,想省到 100 万美元一年需要约 4600 万张工单,而且没算 Lambda 费用。真正能抄的是两个工程细节:一是决策模型只有 4096 上下文,放不下原来的标签说明,于是把 20 个标签各重写成一两句判据、当作单选题的选项发过去,外加一个 "none";二是他们实测 JSON 的 key 顺序能把输出概率挪动最多 0.19,所以现在发请求前先排序 key——这条对任何结构化输出都成立,不限于决策模型。适用前提写得很清楚:闭集标签 + 大流量 + 严延迟,不能推广到 agent。

Google 开 Gemini Decisions API:一次请求评 1000 个问题,输入 $0.10/M、输出不计费

  • 发生了什么:11-11 发布,新模型 gemini-decision-1。它不逐 token 生成文本,而是一次前向算完给概率和置信度。定位写得很直白:路由、工具选择、安全检查、上下文打分这类闭集判断。输入可混文本/图片/音频/视频/PDF,上限 256K;共享输入在一次请求里只计费一次,每多一个问题只加它自己的指令和判据 token。官方说 1 到 100 个问题延迟几乎不涨,端到端 150~250ms。
  • 凭什么算热点:采用度 HN 342 分 / 105 评论(11-12 记录);多源——和 Amazon 那条同周、指向同一个结论,外加 OpenRouter / LangChain / Vercel / LiteLLM / Pydantic AI / OpenCode 的集成在陆续铺,说明工具链侧认了这个形态。结构性:输出不计费这件事本身改变了「分类要不要用 LLM」的算法——以前这类活的成本主要在输出侧。
  • 你该不该动手:立刻试——这是本期最便宜的一次实验,输入 $0.10/M、输出零,测一百条分类的成本约等于零。但先看清三个不支持:没有 context caching、没有 Batch API、没有 Flex / Priority 档,跨请求的重复输入要全额重算。这条直接决定你的调用形态:别一条一条发,要把问题攒成批塞进同一次请求里共享输入,否则省下的全在重复计费里还回去了。Google 自称比走 Interactions API 的 Gemini 3.5 Flash-Lite 便宜近 5 倍——这是官方口径,自己量。

代码审查这块,第一次有人敢拿 token 消耗出来比

阿里把内部用了两年的 AI code review 开源了:Go 写的 CLI,宣称同模型下 token 只要 Claude Code 的 1/9

  • 发生了什么:Apache 2.0。架构是「确定性流水线 + LLM agent」混合——选文件、打包、规则匹配这些走写死的流水线,只把需要动态判断的部分交给 agent;agent 产出的意见还要过一道定位和反思模块校验,才会贴到 diff 的具体行上。内置 NPE、线程安全、XSS、SQL 注入的多语言规则集。装:npm i -g @alibaba-group/open-code-review,CLI 叫 ocr,三平台都有;有 Claude Code / Codex / Cursor / OpenCode 插件,也能当 skill 装。
  • 凭什么算热点:采用度有两个独立口径——GitHub Trending 11-14 新进榜,以及官方称 npm 近 30 天 601K+ 下载(11-15 日报记录)。结构性是我收它的主要理由:上期热点里 Revolut 给的答案是「自托管一个 754B 模型、56 张 B200」,门槛在 2000 人规模;这条给的是同一个问题的另一种答案——不换模型,靠把确定性部分从 LLM 手里拿走来省 token,而且 Delegation 模式下直接用你自己 coding agent 的模型跑,不需要再配一份 key。
  • 你该不该动手:立刻试,十分钟,因为试错成本是本期几条工具里最低的——Delegation 模式不用新 key、不用新额度,装上对一个真实 PR 跑一次就知道。但基准数字要打折看:AACR-Bench 上 OCR + Claude 4.6 Opus 是 33.9% precision / 20.0% recall / 25.1% F1,对照 Claude Code 的 7.23% precision——这个 benchmark 也是阿里自己出的(200 个真实 PR、10 种语言、1505 个经 80+ 资深工程师核过的缺陷),自家工具在自家榜上领先,参考价值有限。你要量的不是 precision,是那个 1/9:在你自己的仓库上跑同一个 PR,对一次 token 账单。另外记住它只提意见、不改代码——它不替代审查人,它是给审查人打前站的。

AWS 把自家云压成了一个本地二进制,而且没人审过那份代码

AWS Emulator 正式可用:本地跑 200+ AWS 服务,不要账号、不要部署,毫秒级返回

  • 发生了什么:11-11 GA。本地起一个程序对外提供 AWS API 端点,现有 SDK / CLI 调用改指过去即可,不依赖 Region。覆盖面从 400 多份 API 模型生成、跨 200 多个服务;不支持的操作返回 501 Not Implemented,状态只放内存,进程停了就没了。协议 CC0 1.0(公共领域)。整份代码由自主 agent 写成,AWS 团队自称一行都没写也没审,而且仓库不收 PR,CONTRIBUTING 只让你提 issue;已知窟窿集中放在 things-that-do-not-work 目录,每个 release 附 fidelity 评分。缘起是 Kiro 用约 15 分钟写出一个能跑的 SQS 模拟器。
  • 凭什么算热点:采用度 HN 763 分 / 227 评论(11-12 记录),多源 The Register、GeekWire 同日跟进。结构性有两层:一层是成本——对照组是今年把免费档塞进账号门槛和非商业限制的 LocalStack,这件事把「本地跑 AWS」的价格打到零;另一层更要紧,是交付模式:一份 AWS 官方发布、无人审查、不收外部 PR 的代码库,这是「agent 写的基础设施」第一次以这个姿态出现在大厂官方仓库里。
  • 你该不该动手:排进这个月,不是立刻试——因为把测试套件的 endpoint 整体改指过去不是十分钟的事,你得先跑一遍看哪些调用吃 501。但用法边界要先划死:它是开发期加速器,不是正确性依据。无人审查 + fidelity 评分 + things-that-do-not-work 目录,这三件事合起来的意思是「行为可能和真 AWS 不一样,而且没人替你兜底」。所以:本地迭代和单元测试用它,集成测试和任何合规相关的验证仍然打真环境。顺带一句,「不收 PR」意味着你踩到的坑只能等它自己修——评估时把这个算进去。

动手教程:把你流水线上最贵的那个分类任务,从聊天模型上搬下来

本周第二组热点的落地版:两小时,量出「这活到底该不该用聊天模型」的三个数

你将做出:一张你能拿去跟人吵的对照表——同一批真实样本,聊天模型 vs 决策模型,各自的准确率、p50 延迟、每千条成本。做完你不是「听说决策模型便宜」,是知道在你这个任务上便宜多少、准确率掉几个点。

准备:

  • 一个闭集分类任务。不是「总结这段文本」,是「从 N 个固定选项里选一个」:路由到哪个 handler、工单打什么标签、这段内容过不过安全检查、这个搜索结果相关不相关。你现在正在用聊天模型干的那个。
  • 从生产日志里捞 50~100 条真实样本,人工标好正确答案。这步最花时间,但没有它后面全是空话。
  • 一个 Gemini API key(Decisions API 输入 $0.10/M、输出不计费,这个实验的模型调用成本基本可以忽略)
  • 你现在那个聊天模型调用的完整 prompt 原文

跟着做:

  1. 先量基线,别先上新东西。 拿你现有的聊天模型调用,对这 50~100 条跑一遍,记三个数:准确率(对照你标的答案)、p50 和 p95 延迟、每条的输入+输出 token。token 数从 API 响应的 usage 字段里取,别估。这三个数现在就是你的参照系——跳过这步直接测新模型,你最后拿到的是一堆没有分母的数字。
  2. 把 prompt 改写成单选题,这是整件事的技术核心。 决策模型只有 4096 上下文,塞不下你原来那段长说明。照 Amazon 的做法改:每个选项重写成一两句判据(不是定义,是「什么情况下选它」),外加一个 none 选项兜底。然后——这条容易漏——发请求前把 JSON 的 key 排序:Amazon 实测 key 顺序能把输出概率挪动最多 0.19。改完对照一下,你会发现原来那段 prompt 里大半是在教模型「怎么说话」,而这个任务根本不需要它说话。
  3. 按批发,不要一条一条发。 Decisions API 没有 context caching、没有 Batch API,跨请求的重复输入要全额重算——所以共享的那段上下文(你的判据表)必须和多个待判样本塞进同一次请求里,它在一次请求内只计费一次。官方说 1 到 100 个问题延迟几乎不涨。这一步做错,你省下来的钱全在重复计费里还回去了,而且你会得出「决策模型也不便宜」的错误结论。
  4. 出表,然后定门槛。 把第 1 步和第 3 步的三个数并排放。接着问一个你必须自己回答的问题:准确率掉几个点是你能接受的? 先写下这个数,再去看结果——顺序反了你会为了结论去挑门槛。如果决策模型掉得太多,别急着放弃:回第 2 步看是不是某几个选项的判据写得太含糊,这类失败绝大多数是判据的问题,不是模型的问题。
  5. 要上线就抄对账那一步。 Amazon 的做法是用 AppConfig 做三路开关,让新旧两个模型同时吃线上流量、结果对账。用你手上任何 feature flag 都行,关键是别直接切——离线 100 条跑对了不代表长尾分布上跑得对。
做完你会:拿到一张真实的对照表,以及一个可复用的判断——你流水线上还有哪些活其实是闭集判断。路由、工具选择、相关性打分、安全预检,这四类是最常见的候选,一个一个过。顺带把第 2 步那条 JSON key 排序用到你所有结构化输出的调用上,这条不限决策模型,是免费的稳定性。
