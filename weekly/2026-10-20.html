模型精讲:Tokenizer 与 BPE——大模型其实没见过「字」,它只认「编号」

你给模型发的每一句话,进门前都先被剁成碎片、换成数字——这一步叫分词(Tokenization)

核心看点:理解 BPE,你就能同时想明白三件困扰新手的事:为什么 API 按 token 计费而不是按字数、为什么模型数不清「strawberry 里有几个 r」、为什么同样一段话中文比英文贵。

它是什么

Tokenizer(分词器) 是大模型的「翻译前台」:你输入的文字在进入模型之前,会被切成一个个 token(词元),每个 token 再换成一个整数编号。模型从头到尾操作的都是这些编号,它根本看不到原始字符。

现在主流模型用的切法叫 BPE(Byte-Pair Encoding,字节对编码)。它切出来的既不是「字」也不是「词」,而是介于两者之间的子词(subword):常见词整块保留,生僻词拆成碎片。

比如 "Hello world" 在 GPT-2 的切法下是 ["Hello", "Ġworld"]——那个 Ġ 是 GPT-2 用来表示「这里原本有个空格」的特殊符号。也就是说,空格也是 token 的一部分。

为什么重要

  • 计费和上下文窗口都按 token 算。「128K 上下文」指的是 12.8 万个 token,不是 12.8 万个字。英文大约 1 个 token ≈ 0.75 个单词,中文通常 1 个汉字就要 1~2 个 token——同样信息量,中文往往更贵。
  • 它解释了模型的一类「智障时刻」。问「strawberry 里有几个 r」模型经常答错,因为在它眼里这个词可能就是 straw + berry 两个编号,字母层面的信息在进门时就被抹掉了。数字算术出错也常有同样的根源。
  • 它决定了模型在你领域里的「效率」。用英文语料训出来的分词器去处理日文或代码,会把东西切得特别碎,同样内容消耗的 token 翻几倍——这就是为什么从零预训练一个模型时,要先在自己的语料上重训分词器。

它是怎么工作的

BPE 的训练过程只有一个动作,不断重复:找出当前文本里出现次数最多的相邻一对,把它合并成一个新 token,记下这次合并。

拿 the cat in the hat 举例:

  1. th 出现了 2 次(最频繁)→ 合并为新编号 256,文本变成 <256>e cat in <256>e hat
  2. <256>e(也就是 the)出现 2 次 → 合并为 257,文本变成 <257> cat in <257> hat
  3. 继续重复……直到达到你设定的 词表大小(vocabulary size) 为止

这些合并记录就是 merges 表。以后遇到新文本,分词器会按学习时的先后顺序(先学的优先级高)把 merges 重新套用一遍——所以同一个分词器切同一句话,结果永远一致。

进阶点一:为什么叫「字节」对编码。 现代 BPE 是 byte-level 的:先把文字转成 UTF-8 字节,得到 0~255 的整数,这 256 个值就是初始词表。好处是任何字符都能表示,永远不会出现 UNK(未知词)——emoji、生僻字、乱码都能被拆成字节兜底。所以词表大小 = 256 + 合并次数 + 特殊 token。GPT-2 是 50,257,GPT-4 是 100,256,GPT-4o 涨到了 199,997。
进阶点二:词表大小是个权衡。 词表越大,同样文本切出的 token 越少(推理更省、更快),但模型最后那层输出矩阵(要对每个 token 算概率)也越大、越占显存。GPT-4o 把词表翻倍,很大一部分收益是给中文、日文等非英语语言「提速降费」。

动手教程:给你的 AI 编程助手写第一个「Skill」,让它学会你团队的规矩

不用写代码、不用部署,一个 Markdown 文件就能给 Claude Code / Codex 装上一项长期技能

你将做出:一个符合 Agent Skills 开放规范的技能包。放进项目后,当你提出相关需求时,Agent 会自动加载它,按你写的流程办事——不用每次都复述一遍要求。

Hugging Face 在 2026 年新开了一门免费的 Context Course(上下文工程课),第一单元就是 Agent Skills。它基于 Agent Skills Specification 这个开放规范(最初由 Anthropic 提出,现已被 30+ 个编程 Agent 采用),所以你写一次,Claude Code、Codex、OpenCode 都能用。

原理一句话:Agent 启动时只读取每个技能的 name 和 description(几乎不占上下文);当你的需求和某个 description 对上了,它才把整个 SKILL.md 读进来执行。这叫渐进式披露(progressive disclosure)——这就是为什么 description 怎么写,直接决定技能能不能被触发。

准备:

  • 一个支持 Skills 的编程 Agent(Claude Code / Codex / OpenCode 任一)
  • 一个终端,会用 mkdir / ln -s 就够
  • 不需要 Python、不需要 API Key、不需要装任何依赖(本例是纯文档型技能)

跟着做:

  1. 建目录。技能名必须是小写加连字符,且目录名要和后面 frontmatter 里的 name 完全一致:

    ```bash

    mkdir -p ~/my-skills/git-commit-style

    cd ~/my-skills/git-commit-style

    ```

  2. 写 SKILL.md。这是唯一必需的文件。开头的 YAML frontmatter 里 name 和 description 是必填项:

    ```markdown

    ---

    name: "git-commit-style"

    description: "Write git commit messages following our team convention. Use when committing code, writing commit messages, or reviewing commit history."

    license: "MIT"

    metadata:

    author: "your-name"

    version: "1.0.0"

    ---

Git Commit 规范

Overview

本技能规定团队的 commit message 格式,在提交代码时使用。

格式要求

  • 标题行:<type>(<scope>): <简述>,不超过 50 字符,结尾不加句号
  • type 只能是:feat / fix / docs / refactor / test / chore
  • 正文:空一行后写「为什么改」,而不是「改了什么」
  • 结尾:关联的 issue 编号,如 Refs: #123

Step-by-Step

  1. 先跑 git diff --staged 看清楚这次改了什么

    2. 判断 type:修 bug 用 fix,加功能用 feat,只动格式用 chore

    3. scope 填改动的模块名(如 auth、api、ui)

    4. 正文解释动机,不要复述 diff

正例

   fix(auth): 修复 token 过期后未跳转登录页

   原逻辑只在首次请求时校验 token,长时间停留页面后
   再次操作会静默失败。改为每次请求前校验。

   Refs: #412

反例(不要这样写)

  • update code(没有 type,没说清改了啥)
  • fix: 修改了 AuthService.java 的第 45 行(复述 diff,不是动机)

3. **装进项目**。用软链接而不是复制——这样你改源文件,技能立刻生效,不用重新安装。不同 Agent 的目录不一样:

   | Agent | 技能目录 |
   |---|---|
   | Claude Code | `.claude/skills/` |
   | Codex | `.agents/skills/` |
   | OpenCode | `.opencode/skills/` |

   以 Claude Code 为例:

cd /path/to/your-project mkdir -p .claude/skills ln -s ~/my-skills/git-commit-style .claude/skills/git-commit-style `` (Windows 直接复制目录,或用 PowerShell 的 New-Item -ItemType SymbolicLink`)

  1. 测试触发。重启 Agent,然后不要提「用 git-commit-style 技能」,就自然地说:「帮我把暂存区的改动提交了」。如果技能生效,它会按你定的格式写 commit message。
  2. 调试 description(最关键的一步)。换一个说法再试一次,比如「写个 commit message」。如果一种说法能触发、另一种不行,问题 99% 出在 description 写得太窄——它是 Agent 唯一用来做匹配的依据。把用户可能的说法都塞进去(本例里 "committing code"、"writing commit messages"、"reviewing commit history" 就是三个不同的触发入口),改完再测,直到两种说法都能稳定触发。
做完你会:理解 Agent 的「技能」本质上就是一份按需加载的说明书,不是插件也不是代码。下一步可以给技能加 scripts/ 目录放可执行脚本(Agent 会直接运行)、加 references/ 放详细文档(正文只放索引,保持 SKILL.md 在 400~800 行以内)。想看真实例子,可以读 Hugging Face 官方开源的技能库。
